ADR-009 Accepted Core Layer
Apex Unit Testing Stack — apex-mockery, SObjectFabricator, FluentAssert
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-05-18 Estado: Accepted Layer: Core / Base Template
Context

Salesforce Apex unit testing has no official framework beyond System.assertEquals and @testSetup. Without shared conventions, test code diverges quickly: some classes use DML-heavy setup that burns governor limits, others mix assertion styles, and dependency isolation is inconsistent — making tests fragile and expensive to maintain.

Three open-source frameworks address distinct testing concerns and compose cleanly together:

  • apex-mockery — a lightweight stub/mock framework for Apex that allows injecting test doubles without touching production code structure.
  • SObjectFabricator — builds SObject graphs entirely in memory without DML, eliminating the governor-limit cost and test setup complexity of database-backed record creation.
  • FluentAssert — a fluent assertion library that produces readable failure messages aligned to acceptance criteria language.
Decision

All Apex unit tests in this project use apex-mockery, SObjectFabricator, and FluentAssert as the standard testing stack. The three frameworks are complementary — each covers a distinct concern — and are required together in every sandbox and in manifest/buildfile.json.

Usage rules:

  • apex-mockery is used to stub any class that crosses a boundary (service layer, callout, database query). The class under test must never depend directly on a concrete dependency that can be stubbed.
  • SObjectFabricator is used for all in-memory SObject creation in unit tests. DML-based record setup (insert, @testSetup) is reserved for integration-style tests that explicitly require a database state.
  • FluentAssert replaces raw System.assertEquals / System.assertNotEquals in all test classes. Assertion chains must be expressive enough that a failure message reads as a violated acceptance criterion.
Alternatives Considered
ApexMocks (FinancialForce)
Mature but heavier dependency; apex-mockery is simpler, has fewer setup requirements, and aligns better with the TAF action-class model where each unit is small and focused.
TestDataFactory (custom static factory)
Common pattern but DML-bound — fabricating 200 records for a bulkification test costs governor limits. SObjectFabricator eliminates this entirely for unit tests.
Raw System.assertEquals: No standard against readable assertions — failure messages like Expected: true, Actual: false are not actionable. FluentAssert failure messages name the field and the expected state.
Consequences
  • All three frameworks must be installed before running any test class. They are listed as dependencies in manifest/buildfile.json.
  • Test classes are faster and do not consume DML/SOQL governor limits in unit test paths.
  • New developers and agents generating test classes must follow the stack — generating-apex-test skill must produce tests using these three frameworks.
  • When a test class uses raw DML setup or System.assertEquals, it is a candidate for refactor under this ADR.
