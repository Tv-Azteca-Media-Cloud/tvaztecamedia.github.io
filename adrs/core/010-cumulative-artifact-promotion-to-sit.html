ADR-010 Accepted Core Layer
Cumulative Release Artifact for SIT Promotion, Baseline Install Validation in Build Org
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-06-02 Estado: Accepted Layer: Core / Base Template
Context

The project promotes metadata across managed environments via immutable release artifacts built from manifest/buildfile.json (Org Development Model — see architecture/CICD.md). Two facts about Salesforce shape this decision:

  1. A Salesforce deployment only applies what is listed in package.xml. The git working tree may hold the full accumulated state of a release, but the artifact deploys exactly the components enumerated in its manifest — nothing more. A sprint delta artifact (manifest scoped to git diff develop-sit...develop) therefore deploys only that sprint's changes, not the whole release.
  2. UAT, PreProd, and Production start without the prior sprints loaded. A sprint delta artifact cannot be promoted to a fresh UAT org — the delta assumes the previous sprints' metadata is already present. It would fail to "stand up from zero."

This created an apparent need for two parallel artifact tracks: a per-sprint delta (base develop-sit) for incremental SIT certification, and a cumulative release artifact (base main) generated at the end of the release for UAT/Prod. The risk identified: if the cumulative artifact is assembled only at release close and first executed in UAT, then UAT becomes the first place that artifact is ever tested as a unit — a big-bang anti-pattern that violates artifact-based promotion ("the same immutable artifact, validated before promotion").

The team also evaluated whether the "install from zero" validation should happen by refreshing SIT to baseline each sprint. This was rejected: SIT is where humans perform functional E2E certification, so SIT must retain the real accumulated functional state. A build org validates only that a deployment applies cleanly — no human tests functionality there. Forcing SIT to serve both roles (stable functional certification AND clean-install validation) is contradictory, because clean-install validation requires destroying the accumulated state that functional certification depends on.

Decision

The artifact promoted to SIT is the cumulative release artifact — the manifest and buildfile.json accumulate all sprint work to date, not just the current sprint's delta.

  • The release manifest is generated against the release baseline (main / the release start commit), producing the full net footprint of the release — not git diff develop-sit...develop.
  • This collapses the "sprint artifact" and "release artifact" into a single artifact type: the release artifact is the last cumulative sprint artifact. There is no separate big-bang assembly at release close — the anti-pattern is eliminated by construction.
  • The same cumulative artifact is promoted unchanged across SIT → UAT → PreProd → Production. It is never regenerated per environment.
  • SIT receives the cumulative artifact on a sprint cadence and retains accumulated functional state — it is the environment of record for human functional certification. The cumulative artifact deploying onto an org that already holds prior sprints is accepted: re-deploying unchanged components is largely idempotent for Salesforce metadata, and re-running the full test suite each sprint is free regression coverage.
  • The "install from zero" validation is delegated to a build org refreshed to baseline (tva-bldngt / tva-bldrel), run continuously (nightly or per sprint). Because a build org is disposable, refreshing it to baseline costs no functional state. This is what proves the artifact stands up in the same conditions a fresh UAT/Prod will face.
  • By the time of the release dress rehearsal (e.g., Ejercicio Despliegue R1, 2026-07-03), the cumulative artifact has been (a) deployed to SIT every sprint and functionally certified, and (b) deployed to a baseline build org continuously and validated as a clean install. UAT sees nothing new.

Net effect: one manifest, validated under two conditions — accumulated state (SIT, functional) and baseline state (build org, install). Not two parallel tracks.

Alternatives Considered
Two parallel artifact tracks (sprint delta for SIT + separate cumulative for UAT generated at release close)
Rejected — the cumulative artifact's first execution as a unit would be in UAT, a big-bang anti-pattern. Also doubles the manifest-generation surface.
Refresh SIT to baseline each sprint to validate clean install there
Rejected — destroys the accumulated functional state that human E2E certification in SIT depends on. SIT cannot serve both the functional-certification and clean-install roles simultaneously.
Validate clean install only in a build org, keep sprint deltas for SIT
Rejected — a build org validates deployment mechanics only; nobody performs functional testing there. SIT must carry the real accumulated functional state, which a delta-based SIT already does but a delta artifact is not promotable to a fresh UAT. The cumulative-to-SIT model gives SIT the same functional state while producing a directly promotable artifact.
Consequences
  • develop-sit loses its role as the delta baseline for promotion. The promotion manifest is generated against the release baseline (main). develop-sit remains, at most, a historical marker; the unfreeze trigger (releaseCreateManual ✓ + releaseDeploy ✓) is unchanged. See architecture/RM-RUNBOOK.md.
  • generate-sprint-manifest must support a cumulative mode (--base main / release-start commit) that produces the full net footprint, replacing delta-against-develop-sit for promotion artifacts.
  • Destructive changes must represent the net end state, not the historical sequence. If sprint S1 creates a field and S3 deletes it, the cumulative manifest must exclude the field and carry its destructive entry. The same buildfile.json runs on both targets: on SIT (which had the field since S1) the destructive deletes; on a baseline build org (where the field never existed) the destructive is a no-op — sf tolerates destructives against non-existent components with a warning. Net consolidation of destructives across sprints is the core work of the cumulative mode.
  • The consolidated buildfile.json must sequence all four crp-* packages in dependency order as a single coherent plan — more complex than an isolated sprint buildfile.
  • Deployment cost grows each sprint as the cumulative footprint expands and re-deploys unchanged components. This is mostly idempotent for Salesforce + Media Cloud metadata, but metadata types with side effects on re-deploy must be spot-checked; the offsetting benefit is free regression from re-running the full test suite each sprint.
  • This model has a hard prerequisite: disposable, baseline-recreatable build orgs (IaC) per SOUL.md. If refreshing tva-bldngt / tva-bldrel to baseline is manual, the continuous clean-install validation will not happen and the big-bang risk returns. Project time must be allocated to this IaC capability.
  • A nightly job must regenerate the cumulative release manifest (base main) and deploy it to a baseline-refreshed build org, extending the existing nightlyDeploy.yml / BLDNGT capability.
