ADR-011 Proposed Core Layer
Multi-Track Coexistence in a Shared Org
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-06-10 Estado: Proposed Layer: Core / Base Template
Context

The client has requested a second development track ("Track 2") that will go live after R1, built by the client's own autonomous team, to give them a baseline from which to evolve independently. Track 2 is intended to "not impact" the current media project. Six facts shape this decision:

  1. A Salesforce org has no tenancy boundary between projects. API names, profiles and permission sets, the sharing model (OWD), the Apex namespace, per-object triggers, the integration user, named credentials, and runtime governor limits are all global within the org. Track 2 and the media project share one Production org (client decision).
  2. This project runs the Org Development Model, not Package Development (2GP). Per ADR-005 and ADR-010, the crp-* "packages" are logical folders, not namespaced 2GP packages. There is therefore no technical enforcement of the boundary between tracks — Salesforce will let a Track 2 flow fire on the media project's Account. Isolation is exactly as strong as the governance discipline imposed on it; it is a result of governance, not a property of the platform. This makes "Track 2 will not impact R1" an aspiration that must be engineered, not an assumption.
  3. The real overlap is Track2-vs-R2, and it is transitory. Track 2 starts construction after Go-Live R1 (2026-07-25), but R2 is still in flight (sprints S6–S8, Go-Live 2026-08-31). The baseline Track 2 inherits is partially stale the day it is handed over, because R2 keeps moving the org underneath it. No R3 is foreseen — once R2 ships, Track 2 is the only project left in the org. The shared-org regime lasts roughly 8 weeks (Jul–Aug); the governance apparatus exists to protect a bounded window, not a permanent state.
  4. Functional coupling is mixed. Track 2 is mostly a new domain but has several contact points with the core (shared fields, pricing, reports, permissions). "No impact" holds only where Track 2 touches nothing shared — which must be made explicit per change, not assumed.
  5. Runtime is shared even when metadata is cleanly separated. A Track 2 trigger/flow on Account runs in the same transaction as the media project's logic on every DML. A poorly written Track 2 action can breach the SOQL/CPU limit of an Account insert belonging to R1/R2.
  6. Revenue Cloud configuration is data, not metadata. Pricing, ContextDefinitions, and decision tables are promoted via SFDMU. Config-as-data lacks the three safety nets metadata has: git surfaces no collision (SFDMU upsert overwrites silently), and graph integrity is fragile (a partial load corrupts the pricing engine transversally). Matching is by stable business GUID (confirmed — no record-Id binding), which neutralizes cross-org identity divergence but does not resolve simultaneous edits or load ordering.
Decision

Two tracks coexist in one shared Production org under a single governance model — logical isolation enforced by a Shared-Metadata Contract, a cross-track Architecture Review Board, and an artifact-based promotion discipline — for the bounded duration of the overlap, after which custody transfers to the client.

Logical isolation — the Shared-Metadata Contract (four classes)

One governance model applied to four classes of shared things, with controls graduated by how fragile each class is:

ClassGit safety netExtra controlChange rule
Metadata (XML)Collision visible in merge—Shared → ARB authorizes; own → free
Apex (TAF)Visible + additive extensionOrdering / bypassNew action class on a shared trigger: ARB authorizes. Editing an R1/R2 action class: prohibited for Track 2
Config-as-data (SFDMU)None — silent upsertGUID namespace partition + single authorshipShared config authored in one place; own config in a reserved GUID range
Runtime (shared transaction)NoneCombined performance testBypass/ordering owned by the steward

Each shared artifact is classified shared / own / prohibited. Track 2 has full autonomy over own, zero authority over shared, and never touches prohibited without the ARB.

TAF as the additive extension mechanism

The Trigger Action Framework (ADR-008) is what makes mixed coupling survivable: because logic lives in discrete, ordered, bypass-controlled action classes, Track 2 can add its own action class to a shared object's trigger without editing the media project's code. Extension is additive, not surgery on shared code. Without TAF, every Track 2 change to a shared object would be an edit to another team's code.

Same repo (non-negotiable); the how is a sequenced open decision

A single repository is required to preserve a single source of truth and git-level collision detection on shared metadata. The mechanism is deferred: the client cannot access GitHub (security policy) but has GitLab. This is a hard gate of sequence — calendar, governance, and responsibilities are agreed first; the GitHub/GitLab mechanism is resolved only after. The leading candidate is a federated model (GitHub authoritative for the core, mirrored read-only into the client's GitLab as an immutable baseline), which would enforce the "prohibited" class by construction. See the open decisions below.

Architecture Review Board (ARB) — single authority over shared

A weekly cross-track ARB (your TA + client TA) is the only authority that approves changes to the four shared classes. Default is rejection: silence is not approval, and every decision versions the Shared-Metadata Contract in the repo. The ARB also:

  • Certifies which Track 2 releases are "100% own" (touch nothing shared), which is what makes the warranty-window B-bounded option executable.
  • Governs back-promotion (see below) as a function, not a separate committee.

The ARB dissolves when the media project exits — there is no longer a "cross-track" to govern.

Convergence by dates + rebase; UAT is the only shared net
  • No shared QA or SIT. Each track keeps its own dev / build / SIT, so neither project's deliverable is contaminated by the other's in-flight (unstable) work.
  • UAT is the single point of convergence and the only environment where the combined state is validated before Production. It accumulates each track's immutable artifact (ADR-010) — artifacts are never merged; each remains a pure, independent deliverable.
  • Monthly synchronized train, alternating Prod windows. A single master Prod calendar serializes windows: one window = one owner = one artifact, order known before construction. The ARB resolves swaps by exception only (hybrid anchored to the calendar). The whoever-ships-second rebases their baseline from Prod and re-validates the combination in their own SIT before their window. This synchronized cadence is the transitory regime; once Track 2 is alone in the org, it may choose any cadence.
  • Back-promotion is bidirectional. Whoever deploys to Prod, the other back-promotes and re-validates before their next release. Governed by the ARB; executed by RM/DevOps with the same sf builds deploy tooling (CICD.md back-promotion principle).
Config-as-data: partition + single authorship

Stable business GUIDs make cross-org matching reliable but do not prevent collision or coordinate change. Therefore: reserved GUID namespaces per track (collision impossible by partition) and single authorship of shared config held by the steward during the overlap (the last upsert wins silently, so shared config cannot have two writers). A hotfix touching shared config goes through the same authorship even when expedited — never a direct Prod upsert, because a mis-ordered emergency load on the pricing graph breaks quoting for both tracks.

Handover in two stages
  • 2026-08-31 (Go-Live R2): platform-custody handover. The client assumes governance, the master calendar, the ARB, config authorship (including shared config-as-data), and change authorization. This closes the media project's construction-and-control commitment. The only residual right retained: deploy of warranty hotfixes on R1/R2.
  • 2026-08-31 → 2026-09-28 (4-week warranty): warranty scoped to the delivered artifact. Your team retains a single-purpose, expiring deploy access to Prod for R1/R2 warranty hotfixes only. Warranty covers defects of your deliverable (R1+R2 as delivered, including defects that block Track 2 from your artifact discovered in their sandboxes/UAT) — not effects of Track 2 changes layered on top. A warranty hotfix touching shared config-as-data is executed by your team but coordinated with the client, who now holds authorship. Every warranty hotfix is forward-merged to Track 2's integration line. Access is revoked on 2026-09-28 — handover complete.
Open decisions (resolved by the client, not by this ADR)
  1. Track 2 to Prod during the warranty window? Two scenarios are presented for the client to choose, owning the risk:
  • A — Track 2 waits (first Prod go-live post 28-Sep): warranty integrity intact, responsibility boundary clean, ~4 weeks delay.
  • B — Track 2 ships in warranty: faster, but dilutes the client's own warranty and introduces incident-origin ambiguity; requires a surgical exclusion clause signed before 31-Aug.
  • B-bounded (bridge): Track 2 may ship in warranty only if the release touches no shared metadata/config (ARB-certified "100% own"). Velocity for the new domain, core warranty intact. Because your team retains warranty-hotfix deploy, Scenario A is the coherent default: if Track 2 mutates Prod during warranty, hotfixes operate on a moving target you no longer own.
  1. Repo mechanism (GitHub/GitLab federation) — deferred behind the sequence gate above.
Alternatives Considered
Separate org for Track 2
Rejected by client decision (shared Production org). Would give physical isolation but is not the chosen topology.
Shared SIT (or shared QA)
Rejected — a shared lower environment would contain the other track's in-flight unstable work, contaminating the validation of each deliverable. Note this is independent of artifact purity (ADR-010 keeps artifacts separate regardless); the rejection is about validation cleanliness. UAT-as-sole-convergence plus dates+rebase achieves combined validation without the contamination.
Separate repo per track
Rejected — loses both single source of truth and git-level collision detection on shared metadata; in a shared org the only reconciler left would be Production itself (the worst case). Same repo is non-negotiable.
Migrate everything to GitLab
Rejected — rewriting GitHub Actions → GitLab CI, GHCR, and secrets mid-flight (R1/R2 live) risks the media project itself. Reserved only for a corporate mandate.
Dedicated config-master org as source of truth
Rejected as a requirement — stable GUIDs let repo-as-SoT survive without an org minting identity. A dedicated authoring org remains an optional convenience only for complex shared config, not a structural need.
Continuous / weekly cadence for Track 2
Rejected — in a shared org with a fragile, non-IaC UAT as the only net, more releases mean more convergence events stressing the weakest net. Monthly-synchronized minimizes convergence events; the normal instinct (short cadence = safer) inverts here.
Separate back-promotion committee
Rejected — fragments the same architect already in the ARB and closing R2; the decision data (what changed in shared classes) already lives in the ARB. Back-promotion is an ARB function with RM/DevOps execution.
Consequences
  • Hotfix path (bidirectional) is a hard prerequisite, operative before 2026-08-31. The RM-RUNBOOK currently marks the hotfix path "PROCESS NOT DEFINED." Two tracks sharing Prod make it urgent and bidirectional: a hotfix on shared metadata is an org event whose blast radius ignores the project boundary. The taxonomy must classify hotfixes by who they affect (own vs. shared), not only by urgency, and define direction, notification, and reconciliation. It remains necessary after exit, operated by whoever then owns the org. This is a condition of the model, not a follow-up.
  • IaC for UAT is known debt; the risk is signed, not hidden. There is no IaC to recreate UAT test data without manual effort. Therefore re-anchoring UAT (after a rejected homologation or a hotfix that bypassed UAT) is an expensive, manual last resort — it cannot be the primary integrity mechanism. The weight shifts upstream to the Shared-Metadata Contract + ARB as the only reliable control. While IaC is unfunded, convergence integrity depends entirely on the ARB; the day the ARB fails, there is no cheap fallback net. This is an accepted, signed risk.
  • Core knowledge transfer (KT) must happen before 2026-08-31, not on the handover day. The client inherits an org running your R1+R2 code with no one on your side maintaining it after August. The design rationale (ADRs, known traps: PS license binding, External Client App recreation, Unicode normalization, ContextDefinitions sync) must be transferred and documented beforehand, or the client inherits an org they do not understand. This is several days of architect effort to budget.
  • Stewardship must be staffed (risk #5) during R2's final stretch. DevOps accompaniment and architecture harmonization are dedicated, named, funded hours that occur in parallel with UAT R2 and Go-Live R2. They cannot be drawn from existing capacity without either degrading Track 2 governance or delaying R2.
  • Responsibility of delivery (client) is distinct from responsibility of platform (yours). You do not answer for whether their feature works; you do answer for that their feature does not break the shared org while the org is shared. The RACI (per artifact class and per process) makes the accountability migration explicit at each milestone: everything transfers on 31-Aug except warranty-hotfix deploy, which transfers on 28-Sep.
  • The model is transitory by design. All heavy governance (ARB, rebase, alternating windows, UAT convergence) exists to protect an ~8-week overlap. After 28-Sep the org has a single owner, governance relaxes, and the client is genuinely autonomous. The deck and the ADR must frame this as three acts (overlap → handover → Track 2 alone), not as a permanent regime.
  • This ADR is Proposed, not Accepted. The model depends on the client accepting the conditions — that acceptance is the purpose of the client deck. It moves to Accepted when the client signs the calendar, governance, responsibilities, and (then) the repo mechanism. The A/B warranty scenarios and the repo mechanism remain open decisions referenced here, not resolved here.
