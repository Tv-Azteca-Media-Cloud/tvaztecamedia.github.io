ADR-006 Accepted Core Layer
Multi-Package Directory Structure Aligned with Media Ad Sales Functional Domains
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-05-14 Estado: Accepted Layer: Core / Base Template
Context

This project implements Salesforce Media Cloud Ad Sales Management on a greenfield org. As with the Comms Cloud implementation (ADR-005), a single force-app/main/default/ directory creates ambiguity about which metadata belongs to which business capability as the solution grows.

Unlike the Comms Cloud solution — which uses TMForum eTOM as its organizing framework — the Media Cloud Ad Sales solution follows a Media Ad Sales functional domain model: a process-oriented decomposition aligned with the advertising industry's standard workflow from prospect acquisition through campaign delivery and billing.

TMForum eTOM is designed for telecommunications and introduces conceptual mismatch when applied to media and advertising processes. Using it for Media Cloud work would confuse agents during functional refinement and produce inaccurate domain classification for User Stories.

Decision

The repository uses four capability-based packages in sfdx-project.json. This structure is intentionally coarser than a domain-per-package model — it balances deployment isolation with team size and operational simplicity.

Process Scope Mapping

Stories are classified into one of two process scopes — the Media Ad Sales equivalent of eTOM RA/OP used in the Comms Cloud solution:

ScopeDefinition
RP (Request-to-Proposal)From Lead or inbound RFP through media plan, proposal assembly, and signed Insertion Order
OC (Order-to-Campaign)From Insertion Order capture through DRO fulfillment to GAM/Meta, delivery monitoring, and billing
Alternatives Considered
Single force-app/main/default/: Rejected — same rationale as ADR-005; does not scale and makes impact analysis difficult for agents.
TMForum eTOM domains (as in ADR-005)
Rejected — designed for telecommunications; conceptual mismatch for media ad sales processes.
Package-per-functional-domain (advertiser / proposal / order / campaign / revenue)
Considered but rejected at current team size — too granular, introduces excessive dependency management overhead. Can be revisited if deployment isolation per domain becomes necessary.
Consequences
  • All agents (including org-knowledge) scanning the repo must search across crp-common/, crp-integrations/, crp-media/, and crp-sales/ — not force-app/.
  • New metadata placement follows the "What Goes Where" table above. Cross-package placement requires TA sign-off.
  • sfdx-project.json must be updated if new packages are added.
  • The refine-functional-story-media and refine-story-media skills use the process scope (RP/OC) for story classification and Jira labeling — not package names.
  • Graphify must index all four package directories when generating the knowledge graph.
  • crp-integrations isolates all external system coupling — when MuleSoft becomes available, the migration scope is bounded to this package.
