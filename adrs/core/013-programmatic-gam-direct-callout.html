ADR-013 Accepted Core Layer
Direct Apex Callout to GAM for Programmatic PG/PD Quote-to-Proposal Flow
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-07-13 Estado: Accepted Layer: Core / Base Template
Context

The RP (Request-to-Proposal) process for Programmatic Guaranteed (PG) and Programmatic Direct (PD) sales types requires sending a createProposalLineItems request to Google Ad Manager (GAM) via its SOAP API (ProposalLineItemService, v202605) when an AdQuote is Approved or Activated.

ADR-001 establishes that Salesforce acts as a passive core — it does not initiate callouts to external systems. All external orchestration is owned by MuleSoft. However, MuleSoft is not available in the current project phase.

ADR-001 explicitly anticipates this scenario: *"Direct Salesforce callouts to GAM or Meta are acceptable as a baseline; they must be flagged for future MuleSoft migration."* (HIGH-LEVEL-E2E-SOLUTION-MEDIA.md)

DRO (Dynamic Revenue Orchestrator) is the standard fulfillment layer for order-to-campaign flows. However, this integration targets the RP phase — specifically the Quote/Proposal stage, before an Order exists. DRO operates on approved Orders, not AdQuotes. DRO cannot fulfill this requirement.

Decision

Implement a direct Apex callout from Salesforce to GAM ProposalLineItemService for the PG/PD Quote-to-Proposal flow, as an interim pattern until MuleSoft is available.

The implementation must comply with the following constraints derived from the project's architectural standards:

  1. Async dispatch via Queueable: The callout is dispatched from a Queueable class (ProgrammaticGamDispatchQueueable implements Queueable, Database.AllowsCallouts) to avoid the *"uncommitted work pending"* runtime error and to decouple callout execution from the trigger context. @future is rejected — it does not accept complex parameters, limiting payload flexibility.
  2. Named Credentials: All outbound callouts use Named Credentials and External Credentials. No inline credentials in code (ADR-003, SOUL.md — Platform-Managed Authentication).
  3. Encapsulated service class: Callout logic is encapsulated in a dedicated Apex service class (ProposalLineItemService). No callout logic in triggers, TAF action classes, or LWC controllers.
  4. TAF for orchestration: The trigger-side detection of the Approved/Activated state transition is implemented as a TAF action class (ADR-008). The action class only enqueues the Queueable — it contains no callout or business logic.
  5. No-block on ineligibility: When the AdQuote does not meet eligibility preconditions (missing Seat ID, floor price, dates, or other required fields), the integration is skipped without blocking the commercial process. The ineligibility reason is recorded on the AdQuote.
  6. Idempotency: A deduplication key (QuoteName + QuoteNumber + Year) prevents double-sends under event replay or reprocessing.
  7. Error persistence: SOAP faults and technical errors are normalized and persisted to a dedicated field on AdQuote, visible to Ad Operations for recovery.
Scope Boundary

This decision covers only the RP phase (AdQuote → GAM ProposalLineItem). It does not affect:

  • Order fulfillment (OC phase) — DRO remains the standard layer for that.
  • Open Auction quotes — explicitly excluded from this flow.
  • Any other GAM or Meta integration.
Alternatives Considered
DRO Fulfillment Workplace
Not applicable — DRO operates on Orders, not AdQuotes. No DRO mechanism exists for the pre-order proposal phase.
MuleSoft as broker
Correct target architecture but not available in the current project phase. This decision is explicitly interim.
Platform Event + external consumer
Would require an external subscriber (MuleSoft or similar) that does not exist. Defers the problem without solving it.
Manual GAM entry by Ad Operations
Rejected — breaks the Quote-to-Proposal traceability requirement and introduces operational risk of data entry errors.
Migration Obligation

When MuleSoft becomes available, the Apex service class callout logic (ProposalLineItemService) must migrate to MuleSoft without touching business logic. The TAF action class and Queueable dispatcher are replaced by a Platform Event publish. This is a forward-compatible design — the encapsulation boundary is already drawn.

The integration map in HIGH-LEVEL-CORE-SOLUTION-MEDIA.md must be updated when the migration occurs to reflect MuleSoft as the broker.

Consequences
  • Retry logic and resilience for this callout lives in Apex (PR1066114-640), not MuleSoft. This is an accepted interim cost.
  • Governor limits for the async Queueable apply. Bulk approval of PG/PD quotes must be monitored for Queueable queue saturation.
  • This pattern is a tracked exception to ADR-001. Any new direct callout to GAM or Meta outside of DRO must reference this ADR and confirm the same RP-phase constraint applies — it cannot be used as a general precedent for OC-phase flows.
