ADR-015 Accepted Core Layer
Data Cloud (Data 360) as an Isolated Add-on Package — crp-d360
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-08-11 Estado: Accepted Layer: Core / Base Template
Context

Data Cloud / Data 360 (D360) is explicitly out of the baseline solution in the governance documents that rule this repository:

  • HIGH-LEVEL-E2E-SOLUTION-MEDIA.md → Explicitly Not in Baseline: "Data Cloud / Data 360 — Out of scope — Add-on Candidate if required."
  • Project Ground Rules → Add-on Candidate Tagging ("features beyond the licensed stack must be tagged Add-on Candidate and must not block baseline delivery") and No Unlicensed Add-on Dependency ("the baseline solution must not have runtime dependency on unlicensed Salesforce products").

D360 work has now been authorized as an in-scope capability. Salesforce metadata for D360 (data streams, data connectors, data transforms, dataspace scopes, calculated insights, etc.) needs a home in the repository. Dropping it into an existing crp-* package would violate the package placement contract (ADR-006) and, more importantly, would risk coupling baseline R1/R2 delivery to an add-on capability — the exact anti-pattern the Ground Rules forbid.

SOUL.md Non-Negotiable #9 requires surfacing a contradiction with an existing governance document to the TA before proceeding, and #10 requires recording a non-obvious architectural choice as an ADR. Adding D360 to the scope satisfies both triggers.

Decision

D360 lives in a new, isolated fifth package crp-d360, added to sfdx-project.json alongside the four ADR-006 packages. It is an add-on package — governed by the following non-negotiable isolation constraints so it never blocks baseline delivery:

Package Structure
PackagePathPurposeDependencies
crp-d360crp-d360/Data Cloud / Data 360 metadata — data streams, connectors, transforms, dataspaces, insightscrp-common

crp-d360 depends only on crp-common (shared platform configuration), never on crp-media, crp-sales, or crp-integrations. No baseline package may declare a dependency on crp-d360.

What Goes Where
Artifact typePackage
Data Streams, Data Connectors, Data Transformscrp-d360
Dataspace Scopes, Calculated Insights, DMOs / mappingcrp-d360
D360-specific permission setscrp-d360
Shared base classes / utilities consumed by D360crp-common (unchanged)
Isolation Constraints (non-negotiable)
  1. No runtime dependency from the baseline. No baseline package (crp-media, crp-sales, crp-integrations, crp-common) may reference crp-d360 metadata at runtime. Passive Core is preserved — D360 never introduces callouts from the transactional core.
  2. Not in the R1/R2 cumulative artifact. crp-d360 is excluded from releases/rN/ until a licensed D360 track/phase is opened. Its absence must never fail a baseline deploy.
  3. Licensing gate. crp-d360 metadata is deployed only to orgs where the D360 license is provisioned. Deploying it to a non-licensed org is expected to fail and is not a baseline defect.
Alternatives Considered
Place D360 metadata inside crp-media: Rejected — couples an add-on to the baseline package, violates the Add-on Candidate Ground Rule and ADR-006 placement contract.
Keep D360 outside the repo entirely (external docs / separate repo)
Rejected — contradicts SOUL.md ("single source of architectural truth"); versioned metadata alongside code is the established model.
Add D360 types to crp-integrations: Rejected — crp-integrations isolates GAM/Meta external coupling for MuleSoft migration bounding; D360 is a distinct capability with its own license and lifecycle.
Consequences
  • sfdx-project.json gains a fifth packageDirectories entry (crp-d360, depends on crp-common).
  • SQUAD_DIRS in both dangerfile.js and dangerfile.release.js must include crp-d360 so squad/dedup validation recognizes it.
  • RELEASE-CALENDAR.md Squad Manifest gains a crp-d360 row (integration branch develop).
  • Graphify must index crp-d360/ when generating the knowledge graph.
  • The release artifact (releases/rN/) does not include crp-d360 until a licensed track is opened — its metadata is developed and versioned but not promoted through the baseline chain.
  • Agents scanning the repo (org-knowledge) must now search across five package directories.
