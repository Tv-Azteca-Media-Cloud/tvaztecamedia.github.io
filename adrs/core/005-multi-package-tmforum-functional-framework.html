ADR-005 Accepted Core Layer
Multi-Package Directory Structure Aligned with TMForum Functional Framework
TV Azteca · Salesforce Delivery Platform · ADP Whitelabel
Fecha: 2026-04-27 Estado: Accepted Layer: Core / Base Template
Context

As the solution grows across multiple functional domains, a single force-app/main/default/ directory creates ambiguity about which metadata belongs to which business capability. This makes it harder to reason about impact, isolate deployments, and onboard agents that need to understand "what exists where."

The TMForum Functional Framework (eTOM) provides an industry-standard decomposition of telecom business functions into Domains and Process Areas. Using it as the organizing principle aligns the codebase with the architectural language already used in requirements and solution design.

Decision

The repository uses multi-package directories in sfdx-project.json, with each package corresponding to a TMForum functional domain. Metadata is placed in the package that owns the business capability it implements.

Shared

Metadata that does not belong to a single domain (shared utilities, platform configuration, integration contracts) lives in a dedicated shared package — following the TMForum Functional Framework naming convention.

Package Naming Convention

Package directory names use lowercase kebab-case aligned with TMForum domain names:

`` force-app/ shared/ # cross-cutting (TMForum standard) sales/ # Sales Domain customer/ # Customer Domain product/ # Product Domain service/ # Service Domain resource/ # Resource Domain ``

Process Area granularity within a domain is expressed through subdirectories, not separate packages, unless deployment isolation requires it.

Alternatives Considered
Single force-app/main/default/: Rejected — does not scale across domains; makes it impossible to reason about ownership or isolate deployments per capability.
Package-per-process-area
Rejected at this stage — too granular for the current team size; introduces excessive sfdx-project.json complexity. Can be adopted incrementally if deployment isolation demands it.
Consequences
  • All agents (including org-knowledge) that need to understand "what exists" must scan across all package directories, not assume a single path.
  • New metadata must be placed in the package that owns the business capability — TA signs off on cross-domain placement.
  • sfdx-project.json must be updated when new packages are introduced.
  • Graphify must be configured to index all package directories when generating the knowledge graph.
