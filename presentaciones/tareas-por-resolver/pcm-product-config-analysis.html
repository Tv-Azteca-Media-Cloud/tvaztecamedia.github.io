Ventajas y desventajas
Dimensión ✅ Enfoque actual (1 producto + AdSpaceSpecs) 🔶 Enfoque del cliente (N productos separados)
Alineación con PCM
  • Patrón recomendado por Salesforce PCM
  • La diferenciación por MEDIO / PLATAFORMA pertenece al AdSpaceSpecification, no al Product2
  • Consistente con el modelo de datos de Media Cloud
  • Anti-pattern: product proliferation
  • El catálogo escala mal — si se agregan canales, se multiplica el número de productos
  • Rompe la jerarquía Product Classification → Product
Mantenimiento del catálogo
  • Cambios en atributos, precios o reglas se aplican una sola vez
  • Agregar un nuevo MEDIO = crear 1 AdSpaceSpec + 1 AdSpaceSpecProduct
  • Menor riesgo de inconsistencia entre medios
  • Cada cambio de atributo debe replicarse en N productos
  • Agregar un nuevo MEDIO = crear un nuevo producto completo con toda su configuración
  • Alta probabilidad de divergencia entre productos a mediano plazo
Experiencia del Media Planner
  • El planner selecciona el producto y luego elige el AdSpaceSpec (requiere entrenamiento)
  • Menos intuitivo si el planner piensa en "quiero el producto de TVAzteca"
  • Vista unificada del producto en el catálogo
  • El planner busca directamente "Banner Display TVAzteca" en el catálogo
  • La selección de MEDIO y PLATAFORMA ocurre en el browse, no en la configuración de la line
  • Alineado al modelo mental del cliente
Reportería y visibilidad
  • Para filtrar por MEDIO en reportes, se necesita navegar por AdSpaceSpec.Name
  • La segmentación por producto no distingue TVAzteca de UnoTV directamente
  • Reportes por producto reflejan directamente el MEDIO
  • KPIs de ventas por medio son inmediatos desde Product.Name
Integración con GAM / DRO
  • El AdServerAdSpaceIdentifier vive en AdSpaceSpecification — que ya existe hoy
  • DRO mapea AdOrderItem → AdSpaceSpec → GAM Ad Unit de forma estándar
  • No requiere lógica custom para resolver el Ad Unit
  • Cada producto necesita su propio AdSpaceSpecProduct bien configurado
  • Si dos productos apuntan al mismo AdSpaceSpec, el mapping no difiere — la separación en productos es cosmética respecto a GAM
Qualification Rules y Pricing
  • Una sola regla de qualification cubre todos los medios
  • El precio base se gestiona en un solo precio de catálogo
  • Las qualification rules deben configurarse para cada producto por separado
  • Los Price Book Entries se multiplican proporcionalmente
Escalabilidad
  • Agregar Claro Sports CTV = 1 nuevo AdSpaceSpec + 1 AdSpaceSpecProduct
  • El catálogo crece en datos de inventario, no en productos
  • Agregar Claro Sports CTV = nuevo producto con todos sus atributos, precios y reglas
  • Con 10 medios × 3 plataformas = 30 productos a mantener solo para Banner Display
⚖️ Posición técnica recomendada
La configuración actual en la org es técnicamente correcta y sigue el patrón recomendado por Salesforce PCM. La solicitud del cliente de crear N productos separados responde a un modelo mental de negocio válido, pero introduce complejidad de mantenimiento que se vuelve costosa conforme el catálogo crece.

La ventaja real del enfoque del cliente es la experiencia de navegación en el catálogo (el planner ve productos por medio). Esto puede resolverse con Product Variants o con filtros de Product Discovery por AdSpaceSpec, sin necesidad de duplicar productos.
"El catálogo tiene 1 producto 'Banner Display'. La diferenciación por MEDIO y PLATAFORMA se modela vía AdSpaceSpecProduct, que mapea cada combinación al Ad Unit de GAM correspondiente. Crear N productos separados duplicaría el costo de mantenimiento del catálogo sin cambiar el comportamiento funcional de DRO — ambos enfoques mapean al mismo Ad Unit al momento del fulfillment."

Ruta MultiAds — escenarios adicionales a evaluar

El integration provider TVAI_MultiAdsOrderIntegrationProvider expone un paso DRO independiente (Crear Order en Multi Ads, Sequence 3 en TVAI_DefinicionCrearOrdenMDS). 🔍 3 — Revisión requerida: código R2 (Media Plan → Order)

El pipeline Media Plan → Order construido en R2 asume el modelo actual de 1 producto + N AdSpaceSpecs. Los siguientes componentes deben revisarse con profundidad antes de adoptar el anti-pattern — varios de ellos usan ProductCode, AdSpaceSpecificationId, o la relación AdQuoteLine → AdOrderItem de formas que podrían verse afectadas.

Componente Paquete Riesgo Punto de revisión
TVAI_QuoteToOrderService crp-integrations Alto Crea AdOrderItemAdSpaceSpec junction records a partir de AdQuoteLine → AdSpaceSpec y copia AdOrderLineTargetValue desde AdQuoteLineTargetValue. Con N productos / 1 AdSpaceSpec por producto, la lógica de resolución del spec y los defaults de targeting necesitan validación. Además, el match de líneas con Data Cloud (AdQuoteLine.TVAM_GamLineItemId__c) requiere pruebas end-to-end.
TVAI_QuoteToOrder_GAMAcceptance crp-integrations Medio Flow triggered por Data Cloud (ssot__SalesOrder__dlm). La decisión "¿Ya existe Orden?" es agnóstica al producto. Sin embargo, el bridge AdQuoteLine.TVAM_GamLineItemId__c que usa para hacer match de líneas en Data Cloud requiere validación cuando hay múltiples productos con 1 spec cada uno — potencial ambigüedad en el matching.
TVAI_GamProposalLineItemService crp-integrations Alto Construye el payload GAM ProposalLineItem desde AdQuoteLine (campos: SponsorshipType, MaxDuration, AdSpaceSpecificationId). Con el anti-pattern, cada producto debería tener exactamente 1 AdSpaceSpecProduct — validar que el servicio resuelva correctamente ese único spec y que el mapeo de tamaños creativos (creativeSizeSpec()) no pierda resolución.
TVAI_ProgrammaticGamHelper crp-integrations Bajo Resuelve creative sizes por AdQuoteLine → AdSpaceCreativeSizeType y escribe el resultado en el payload GAM. Opera a nivel de AdSpaceSpec, no de Product — agnóstico al enfoque de catálogo. Sin cambios esperados si los AdSpaceSpecs no cambian.
TVAM_EnviarAprobacion crp-media Medio Evalúa Gate 1 (descuento de línea) y Gate 2 (rentabilidad). Usa ProductCode para consultar la decision table TVAM_ProductosRangoPrecios. Con N productos y N ProductCodes nuevos, cada código debe existir en esa tabla antes de ir a producción — de lo contrario la aprobación comercial no puede evaluar el rango correcto.
TVAM_CotizacionAlCrear crp-media Bajo Asigna el RecordType del AdQuote (Programática vs. Venta Directa) y propaga Implementador/Trafficker desde la Opportunity. La clasificación opera sobre el AdQuote, no sobre el producto — sin impacto esperado. Verificar que no exista lógica de clasificación basada en ProductCode o ProductClassification.
TVAM_PropagImplementadorTraffickerOrder
TVAM_PropagEventoOrder 		crp-media Bajo Flows que propagan campos (Implementador, Trafficker, Evento) de Quote a Order en la creación. Operan sobre campos del AdQuote / Order — agnósticos al producto. Sin impacto esperado.
⚡ 4 — Automatización de campos: oportunidad del anti-pattern

Con el enfoque de 1 producto por combinación MEDIO × PLATAFORMA, el AdSpaceSpecificationId en AdQuoteLine se puede derivar automáticamente desde el producto seleccionado — cada producto tendría exactamente 1 AdSpaceSpecProduct vinculado. Esto elimina el paso manual de selección de spec, una ventaja operativa real del anti-pattern que vale la pena diseñar bien si se decide adoptarlo.

Campos candidatos a auto-poblarse en AdQuoteLine
AdQuoteLine.AdSpaceSpecificationId AdQuoteLineCreativeSizeType (tamaños por defecto del spec) AdProductDefaultTargetCategory / AdProductDefaultTargetValue AdQuoteLine.TVAM_GamLineItemId__c (en flujos PG/PD)
Opciones de mecanismo
1
Flow Record-Triggered en AdQuoteLine  Recomendado · sin código
Before-save flow en AdQuoteLine (Create / Update cuando Product2Id cambia): busca el único AdSpaceSpecProduct vinculado al producto y actualiza AdSpaceSpecificationId. Mantenible por admin, no requiere Apex. Ideal si la regla 1 producto → 1 spec se mantiene estricta. Limitación: si un producto tiene más de 1 AdSpaceSpecProduct, el flow necesita criterios adicionales de selección que lo volverían complejo.
2
TAF Apex Action  Robusto · testeable
Una clase action del Trigger Action Framework (TVAM_AutoPopulateAdQuoteLineSpecAction) invocada desde un record-triggered flow. Permite manejar casos edge: múltiples specs por producto, lógica de selección por contexto (período de vuelo, medio), y operaciones bulkificadas. Requiere test class con SObjectFabricator + apex-mockery según ADR-009. Recomendado si la lógica de selección involucra más de una condición o si se necesita poblar múltiples campos derivados.
3
Decision Table lookup  Declarativo
Si el mapping producto → AdSpaceSpec es puramente data-driven y ya existe en los registros del catálogo (AdSpaceSpecProduct), puede exponerse como paso de lookup dentro del pricing procedure o un sub-flow de Product Discovery. Cuidado: mezclar lógica de auto-población con el pricing procedure añade complejidad al flujo de cálculo de precios — evaluar con el TA antes de usar esta ruta.
📌
Prerrequisito para cualquier mecanismo de automatización

La automatización solo es viable y mantenible si la regla 1 producto → 1 AdSpaceSpecProduct se mantiene de forma estricta en el catálogo. Si un producto puede tener múltiples specs (ej. un bundle de medios), la automatización requiere lógica adicional de selección y el beneficio operativo se reduce significativamente.

Premisa del Proyecto

Implementación Out-of-the-Box de Salesforce Media Cloud y Revenue Cloud

TV Azteca Media contrató una implementación greenfield sobre Salesforce Media Cloud Ad Sales Management y Revenue Cloud Advanced (RCA). El acuerdo de proyecto establece como principio rector el uso de capacidades estándar de la plataforma antes de cualquier desarrollo a medida — Standard-First. Toda desviación de los objetos, modelos y patrones nativos de Salesforce debe justificarse técnicamente y aprobarse de forma explícita.

Product Catalog Management (PCM)
El catálogo de productos sigue el modelo nativo de PCM: un producto representa qué se vende; las AdSpaceSpecProduct mapean dónde y cómo se entrega en GAM. Multiplicar productos por combinaciones de medio × plataforma contradice este modelo y no es una práctica recomendada por Salesforce.
